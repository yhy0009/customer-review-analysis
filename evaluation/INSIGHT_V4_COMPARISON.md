# 인사이트 품질 개선 결과 — 근거·누락 검사와 제안 제한

2026-09-14 KST(원시 기록은 2026-09-13 UTC)에 `gpt-5-mini` 라우팅 서버로 검증했다.
최종 v4는 기존에 빠지던 불편을 세 사례군의 이슈에 보존했고, 긍정 전용·사실 전용 입력에
허위 불편을 만들지 않았다. 개선 제안은 확인된 불편에 대한 점검·처리 절차 후보로 제한했다.
아래 의미적 대조는 assistant의 보조 검토이며 사람 검토 상태는 계속 `pending`이다.

## 무엇을 바꿨는가

v2의 단일 요약을 v3에서 ‘리뷰별 근거 추출 → 최종 요약’으로 바꿨다. 모든 리뷰를 검토했는지,
인용이 해당 원문에 존재하는지, 추출한 모든 불편 label이 이슈에 남았는지 검사한다. 장점이
확인됐으면 요약에도 최소 하나가 남아야 한다. 이 단계에서 누락은 개선됐으나 한 제안에 원문에
없는 앱이 등장했다. 최종 v4는 개선 제안도 코드가 만드는 제한된 후보에서 선택하게 했다.

후보는 불편 label에 ‘발생 조건 확인·재현 점검’ 또는 ‘처리 절차·안내 개선’을 붙인 문장이다.
제안의 구체성은 제한되지만, 제품 내부 구현이나 고장 원인을 모르는 상태에서 해결책을
지어내지 않는다. 장점·불편 label의 의미까지 기계적으로 입증하는 것은 아니므로 원문 대조가
여전히 필요하다. 자유로운 기술적 해결안이나 효과 보장은 생성하지 않는다.

외부 `InsightResult`와 키워드 집계 규칙은 그대로다. 정상 추출은 API 2회이며, 요약만 실패하면
그 단계만 재시도한다. 입력·근거·후보가 한도에 들어가지 않으면 내용을 숨겨 자르지 않고 실패한다.
처음 18건 근거 추출이 30초 제한에 걸려 공통 `ai.timeout_seconds` 기본을 90초로 조정했다.
감정 분석도 이 설정을 사용하므로 실패 대기시간이 늘어날 수 있다. 명시한 설정값은 존중한다.

## 자료와 실행 구분

- 기존 18건과 라벨프린터 9건은 이미 관찰한 회귀 사례다. 원문과 저장된 감정·키워드를 유지했다.
- 추가 블렌더 6건은 v3 첫 응답을 보기 전에 [원문과 기준](VALIDATION_V2.md)을 고정했다.
  SHA-256: `87bf7c29dff2608671b0d4a7df700452d89ad92415a19e30fe9de315a3697d7b`.
- v4는 같은 6건을 다시 사용했으므로 새 독립 검증이 아니다. 모든 라벨은 assistant 초안이다.
- 최종 v4 재실행은 기존 저장 분석을 사용하고 분류를 다시 호출하지 않았다.
- v2/v3 짝 비교에서 원본 입력 해시는 일치했다. v4 재실행의 원본 입력 해시도 해당 v3와
  일치하지만 두 단계 요청 내용 전체가 같은 실험은 아니다.
- 모든 실행은 `max_retries=0`으로 실패 자체를 기록했다. 기본 서비스의 제한된 재시도는
  별도 자동 테스트로 확인했다. 실패한 실행을 덮어쓰거나 유효 JSON으로 임의 수리하지 않았다.

## 실패도 포함한 결과

35회 중 전송 실패는 1회(30초 timeout), 근거 응답 검증 거부는 2회였다.

- [v3 18건 첫 실행](results/2026-09-14/v3-reviews-30s-failed.json): 근거 요청 timeout.
- [v3 9건 첫 실행](results/2026-09-14/v3-printer-30s-failed.json): 근거 검증 거부.
  이 시점에는 거부 원문을 저장하지 않아 JSON 문제인지 인용 문제인지 사후 구분할 수 없다.
- [v4 9건 첫 실행](results/2026-09-14/v4-printer-invalid-json.json): 마지막 리뷰 객체의 닫는
  중괄호가 빠진 JSON을 거부했다. 이 기록에는 진단용 모델 응답을 보존했다.

최종 v4의 6개 실행 중 5개가 성공했고 1개는 위 JSON 오류로 실패했다. 라벨프린터를 새 경로에서
다시 실행했을 때 통과해 최종 5개 범위의 결과를 확보했다. 이를 첫 시도 성공률 100%로 표현하지
않는다. API가 응답을 반환했더라도 의미·형식 검사에서 실패할 수 있다.

전체 요약은 160자 제한이므로 모든 세부 불편을 반복하지 않아도 되지만, 이슈 목록에는 추출한
불편 label이 모두 남아야 한다. 표현이 비슷한 label은 남을 수 있으며 주제 정규화를 했다고
주장하지 않는다. ‘원문 인용 존재’와 ‘label 포함’ 검사는 의미적 참/거짓 판정과 구분한다.

## 코드와 실제 흐름 검증

- 자동 테스트 260개 통과. 근거 순번 누락·중복, 다른 리뷰 인용, 부정 근거 누락, 장점 누락,
  최종 불편 누락, 허용 후보 밖의 기술적 제안, 입력 초과, 단계별 재시도·실패 보존을 검증했다.
- 새 6건은 실제 분류 기대 라벨 6/6 일치, Macro F1 1.000이었다. 이는 작은 합성 세트 결과다.
  [전체 흐름 기록](results/2026-09-14/v3-new-full-pipeline.json)의 SQLite 저장·재실행 skip·
  키워드 정합성·리포트·원본 분석 보존 6개 구조 검사가 통과했다.
- 최종 v4 블렌더 결과로 TXT·Markdown 리포트를 다시 생성해 저장 통계와 키워드·대상 수가
  같은지 확인했다. 평가 DB 복사본을 사용하고 원본 DB 바이트 해시가 유지됨을 확인했다.
- 원래 18건 데이터·9건 데이터·과거 응답과 v1/v2/v3 프롬프트를 보존했다.

## 재현

```bash
# 저장된 분류를 재사용하여 현재 흐름만 확인: 최대 2회, 새로운 출력 경로 필요
python scripts/compare_insights.py --live --current-only \
  --dataset evaluation/reviews.validation.v2.json \
  --saved-evaluation evaluation/results/2026-09-14/v3-new-full-pipeline.json \
  --timeout-seconds 90 --output /tmp/cra-v4-new-repeat

# 긍정 전용 범위를 보려면 위 명령에 --case-id bp01 추가
# 사실·미사용 전용은 --case-id bu01 --case-id bu02 추가
# --current-only를 빼면 보존된 v2 단일 요청과 비교: 최대 3회
```

현재 버전은 `review-insights-v4`다. 이전 버전을 명시한 호출자는 v4 또는 `None`으로 변경한다.
실행 결과는 모델 변동의 영향을 받는다. 최종 다섯 범위에서 지정한 회귀 문제를 해결했지만,
새로운 실제 고객 데이터에서도 누락·가정이 없다는 보장이나 사람 품질 승인을 뜻하지 않는다.
